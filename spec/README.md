# Operation spec

Every write to the catalog is an **operation**: an atomic batch of entity changes with an intent label. This folder is the reference that every implementation (the Rust app, the future PHP server, any third-party client) must follow. It is licensed under [MIT](LICENSE), unlike the rest of the repository, so anyone can build a compatible client or server.

| File | Contents |
|---|---|
| `operation.schema.json` | JSON Schema of an operation: envelope, changes and the fields each entity accepts |
| `conformance/operation-validation.json` | Operations with the expected validation result (`valid`, or `invalid` with an error code, change index and field) |
| `conformance/signatures.json` | Signed operations with the canonical bytes and the verification result every implementation must get |
| `conformance/library-merge.json` | Operations from several libraries, delivered in different orders, with the rows every order must end in |
| `conformance/merge.json` | The merge rules inside one library (field by field, last writer, delete wins, repeated delivery, broken references, one HLC per operation), in the same shape |
| `conformance/permissions.json` | Operations from devices with different roles, delivered in different orders, with which ones are applied and which become requests |
| `conformance/draft/` | Cases for the next version of the format, when there are any. Not loaded by the implementations |

## Rules the schema cannot express

- Every operation belongs to **one library** (`library`, the unit that is shared, synced and permissioned). Changes never name a library themselves: a `library_id` field in a change is an unknown field.
- A change to the **`library` entity** must have the operation's own library as its id: an operation can create, rename or delete only its own library.
- Entity ids only need to be unique **within a library**: the same id in two libraries is two different rows.
- **Deleting the library** (a `delete` change on the `library` entity) removes the library and everything in it on every device that has it. Who may do it is a permission rule, defined with roles. Leaving a library is not an operation on it: the device simply stops having it (and, with roles, the person's membership ends).
- A **`device`** row can only be created by that device itself: its id must be the device in the operation's `hlc` (`other_device` otherwise). The row carries the public key the device signs with, and the operation that creates it is signed with that key, which proves the device holds it.
- A **`mark`** (what one person notes about one work, D68) has an id derived from its person and work: the UUID v5, in the namespace `7b2f0c1e-4d8a-4f3e-9c61-2a5d8e0b4f17`, of the text `<member_id>:<work_id>` in lowercase. A mark change that sets `member_id` or `work_id` must set both, and its id must be the derived one (`wrong_id` otherwise). So the same person marking the same work on two devices writes the same row. A mark is **never deleted by a change** (`undeletable`): the tombstone would keep that id, and so that person, from ever marking the work again. Clearing a mark sets its fields to `null`, and creates send only the fields that are set, so an empty value does not overwrite what another device of the same person set. Marks go when their work or their person is deleted. Example: member `01997c7e-0000-7000-8000-000000000013` and work `01997c7e-0000-7000-8000-0000000000d1` give `9ae21929-1e26-5646-8c48-52cf10f8e911`.
- A **rating** is a whole number from 1 to 5 (`wrong_type` otherwise).
- An **`isbn13`** is thirteen ASCII digits, without hyphens, and a copy's **`quantity`** is a whole number of at least 1 (`wrong_type` otherwise).
- A **text** value never contains U+0000, because PostgreSQL's JSONB cannot hold it (`wrong_type` otherwise). The six characters `\u0000` typed by a user are ordinary text.
- An **intent** is two or more words joined by single dots; a word is one or more lowercase ASCII letters or underscores, and nothing else (no digits, no capitals, no line break after the last word): `book.add`, `a_b.c_d.e` (`invalid_intent` otherwise).
- The **`hlc`** has the text form `<16 digits>-<8 hex digits>-<device>`, **the device being a UUID written `8-4-4-4-12` in lowercase hexadecimal** (SEG-029). An operation whose `hlc` is not in that form (one with a device in capitals, or that is not a UUID, included) is not an operation (it does not deserialize), so it has no validation case; `conformance/permissions.json` has one that expects it `rejected`. The same holds for every other place a device id is written: `library.cloud_device_id` (or the empty text that takes it away), `revocation.device_id` (`wrong_type` otherwise) and the `id` of a `device` change (`invalid_id` otherwise) are lowercase UUIDs. **Device ids are compared exactly** (no case folding, no «the first row that matches») in the judge, in the fences and revocations, and wherever the cloud's device is looked for: one device has one writing, so two writings can never be two devices (one with the cloud's power and one without).
- **Create** must include every required field of the entity.
- **Required fields** can never be set to `null`.
- **Dates** must exist on the calendar (`2026-02-30` is invalid).
- **`previous`** (D87) is the id of the latest operation of the same device in the same library when the operation was made, or `null` for the first. The key is **required** even when it is null: an operation without it is not an operation (it does not deserialize). It must be a UUID and never the operation's own id (`invalid_previous`). It is part of what the signature covers. A receiver that does not have `previous` yet makes the operation **wait** (not stored, the rest of its author's with it) and one whose `previous` belongs to another device or library, or is not earlier in the clock, refuses it; a null `previous` from an author that already has operations, or two operations with the same `previous`, are accepted (forks are left to the fences). See `docs/architecture/sync.md`.
- A device's **`trusted_through`** (D84, D87) is the id of the last operation of that device the administrator had when it lost power, or `""`. Of that device's operations dated before the one that sets it, only the marked one and its ancestors through `previous` count; any other is a request.
- Errors are reported in this order: operation id, library, previous, intent, empty changes, then each change in order (id, other library, other device, action, fields in alphabetical order, missing required fields).

## Error codes

`invalid_id`, `invalid_library`, `invalid_previous`, `invalid_intent`, `no_changes`, `other_library`, `other_device`, `unknown_field`, `missing_field`, `null_required`, `wrong_type`, `empty_update`, `fields_on_delete`, `wrong_id`, `undeletable`.

## Signatures

Every operation is signed by the device that made it (the device in its `hlc`), with Ed25519:

1. Take the operation **without** its `signature` field.
2. Write it as **canonical JSON** (RFC 8785): object keys sorted by UTF-16 code units, no whitespace, strings escaped only where JSON requires it (`\"`, `\\`, `\b`, `\f`, `\n`, `\r`, `\t`, and `\u00xx` in lowercase for the other control characters), everything else written as is, in UTF-8. Operations only contain strings, integers, booleans and nulls.
3. Sign those bytes. `signature` is the 64-byte signature in base64url without padding.

The public key of each device travels with the library as a **`device`** row (32 bytes, base64url without padding). A device registers itself in the first operation it signs in a library. Receivers check the signature against the key registered for the author; the first key registered for a device is the one that counts. A key never changes: an operation that sets a different `public_key` on a registered device, its own included, is **refused**. Another field, `vouched_key`, is what someone else says they saw for that device when they said whose it is; it never replaces `public_key` and decides only whether the device is its person's (rule 13 of «Roles and permissions»). A device that is not registered yet is known only through the `device` row it creates **for itself** in the operation (an update of its own row, or the row of another device, does not register it), and an operation from a device whose key cannot be found that way is refused. The permission cases pin this down with `rejected` operations. Operations from before signatures existed carry none; how they are treated once a library has roles is still to be decided.

`conformance/signatures.json` has, for each case, the operation, the public key, the exact canonical text and the result: `valid`, or `invalid` with `missing`, `bad_key`, `malformed` or `mismatch`. The keys in it come from fixed test bytes and must never be used for anything else.

## Roles and permissions

Every device checks each operation it receives, and each one it makes, against the roles of the library (D55, D73 in `docs/DECISIONS.md`). All devices reach the same verdict, whatever the order operations arrive in.

1. **A library is born founded, by one key (D97).** There is no library without roles. The first operation of a library is its **founding**: one operation, signed by the device that makes it, that

   - creates the `library` row with a `founding_nonce` (16 random bytes, base64url without padding),
   - creates the library's first person, with `role: admin`, and
   - creates the author's own `device` row, with its `public_key` and `member_id` pointing at that person and `vouched_key` equal to its own `public_key` (rule 13).

   The founding is the only operation allowed while nobody in the library has a role, and it is allowed only if **the library's id derives from the key and the nonce of its author**: take the 32 bytes of the Ed25519 public key the author gives in its own `device` row of that operation, followed by the 16 bytes of the nonce; compute their SHA-256, keep the first 16 bytes, set `byte[6] = (byte[6] & 0x0f) | 0x80` and `byte[8] = (byte[8] & 0x3f) | 0x80`, and write them as a lowercase UUID, as rule 12 does for the cloud device but with the nonce. The key `iojj3XQJ8ZX9UtstPLpdcspnCb8dlBIb83SIAbQPb1w` with the nonce `AAECAwQFBgcICQoLDA0ODw` gives `2c33de53-4834-8a05-b014-c42dc60bd4e1`. Nobody can found an id that does not derive from their key, whatever date the operation carries: a founding dated before the real one, by a device the id does not derive from, is a request like any other operation of nobody. An operation in an unfounded library that is not a founding is a request, and so is a founding of a library that already has a person with a role. A **fenced** author (rule 6) founds nothing. `library.founding_nonce` is written once, by the founding, and **nobody writes it afterwards**, an administrator included. A library whose history does not start with a founding that passes this rule never has a role: nothing is applied in it but the devices registering themselves (rule 4).
2. **Who wrote an operation** is the device in its `hlc` (signed). Its **person** is the member its `device` row points to (`member_id`), **provided its `vouched_key` allows it (rule 13) and the person still has access (rule 14)**, and its **role** is that member's `role` at the moment of the operation. A device linked to no member counts as a **reader**, and so does one whose `vouched_key` does not allow it. An operation without a signature is never allowed: it is refused before it is judged (D56).
3. **Roles** (`member.role`: `admin`, `editor` or `reader`; `member.can_share`: true or false):
   - **admin** may do everything, including roles, who owns each device, access (`revocation`), the `library` row and deleting the library.
   - **editor** creates and edits the catalog. It deletes only rows its person created: a row whose first create change came from a device of the same person. **Not a `member`:** deleting a person is for administrators (SEG-034), even one the editor created herself, because a deleted person leaves her devices without a person and her account without a library.
   - **reader** changes nothing in the catalog: what it tries becomes a request.
   - **Everyone keeps their own marks** (D68), whatever their role: a device with a person creates, changes and deletes the `mark` rows of that person (a create names it in `member_id`), and only administrators touch other people's. A device linked to no member may not.
   - **Nobody gives more than they have:** changing `role`, `can_share`, `access_withdrawn` (rule 14; its one exception is a person leaving by themself, rule 15) or a device's `member_id` (and the `vouched_key` that goes with it, rule 13) is for administrators.
4. **Every device registers and renames itself**, whatever its role: its own `device` row, without `member_id` or `vouched_key`.
5. **All or nothing:** if any change in an operation is not allowed, none is applied and the whole operation becomes a **request**.
6. **Roles as they were at that moment:** each operation is judged against the roles in force at its HLC, following the log in HLC order. When an operation arrives older than what a device has already applied, the device re-evaluates that library from its log.
7. **Nothing is lost:** an operation that becomes a request stays in the log and travels on to other devices like any other.
8. **Resolving a request** is for administrators: an operation that creates the `change_request` row whose id is the requested operation's id, with `status` `accepted` or `rejected`. Accepting repeats the requested changes in that same operation, so they are applied as the administrator's. A request with no `change_request` row is pending.
9. **Withdrawing a request** is for whoever asked: a device of the same person as the requested operation's author may create that `change_request` row with `status` `withdrawn`, and nothing else. It is the only `change_request` row a non-administrator may write.
10. **The asker's note travels inside the request:** the requested operation may carry a `change_request` row with its own id and only a `note`. Only an administrator could create that row, so the operation always stays a request; accepting repeats the requested changes without it.
11. *Reserved.* The seal of D94 existed only for the step from a library without roles to one with them. With the founding (rule 1) there is no such step, and D97 removed it; the number stays so that the references to rules 12, 13 and 14 do not move.

12. **The cloud's power (D76, D95).** The **cloud device** of a library is the one `library.cloud_device_id` names at the moment of the operation, **and only if the key registered for that device in the library (the `public_key` of its `device` row) is the one its id derives from**; with the field empty, the device not registered, or registered under that id with another key, there is none. **The id derives from the key:** take the 32 bytes of the Ed25519 public key (the decoded key, not its base64 text), compute their SHA-256, keep the first 16 bytes, set `byte[6] = (byte[6] & 0x0f) | 0x80` and `byte[8] = (byte[8] & 0x3f) | 0x80`, and write them as a lowercase UUID (8-4-4-4-12; a version 8 UUID). The key `iojj3XQJ8ZX9UtstPLpdcspnCb8dlBIb83SIAbQPb1w` gives `34750f98-bd59-8cfc-946d-a45aaabe933b`. That ties the id the administrator writes to a key nobody can forge: a modified app can register any id with a key of its own, but cannot give a key whose derived id is the cloud's, so only the real cloud, which holds that key, has the power. Registration comes first, in its own operation: one that registers the cloud device and in the same operation writes `account_id` is judged before the device is registered, so it is a request. Whoever may change the `library` row writes the field (an administrator). Besides what any device of nobody may do (rule 4), the cloud device may make exactly two kinds of change: a `member` `update` that touches **only** `account_id` (set it or empty it), on a person that exists; and a `device` `update` that touches **exactly `member_id` and `vouched_key`**, both set to a non-empty text, on **another** device that at that moment has an empty `member_id`, pointing at a person that at that moment has an `account_id` **and has not had their access withdrawn (rule 14)**. The cloud vouches for what it links (D96): with `member_id` alone, `vouched_key` alone, either empty, or one field more, the operation is a request. The judge does not check whose the key is: that is rule 13 (if the key it vouches for is not the one the device is registered with, the device belongs to nobody, and the operation, which is applied, gave it nothing). It may not change roles, `can_share` or `access_withdrawn`, reassign a device that already belongs to somebody, take a device's person away, write `trusted_through`, delete, touch the `library` row, the revocations or the catalog. Its own device stays a device of nobody. «A device of nobody» in this rule means a `member_id` that is empty, as always, not the condition of rule 13. **`member.account_id` is written by the cloud device alone**: a change that touches it from any other device, an administrator's included, makes the operation a request, and so does a `create` of a member that carries it. Values of both fields are compared without regard to case, like every id. Fences hold for the cloud as for any device: an operation of it that falls under one is judged as nobody's, so it has none of this power; and the app takes the power away (emptying or changing `library.cloud_device_id`) in the same operation that fences the old cloud device, also when that device is not registered yet (empty mark). All or nothing, as always. Without roles nothing changes (rule 1): everyone may write both fields.

13. **The vouched key (D96).** `device.vouched_key` (text, nullable, with the shape of `public_key`, compared byte by byte) is the public key that whoever said whose the device is had registered for it. It is written **in the same change as `member_id`, by whoever may write `member_id`** (rule 3: an administrator); a change that touches it and does not come from there makes the operation a request, as it does for `member_id`. A device never writes its own with roles (rule 4), and taking the person away (`member_id` null) empties it in the same change. The cloud may not write it (rule 12). It does not touch `public_key`, whose rule is the same: what the device registers of itself, and never changes. **A device belongs to the person its `member_id` names only if its `vouched_key` is empty (an assignment from before D96) or equal to the `public_key` it is registered with in the library; if it is set and differs, or the device is not registered, the device belongs to nobody**: it counts as a reader, keeps no marks, and so on, in everything the judge asks about the person or the role of a device (rules 2, 3 and the deletes of an editor's own rows). Like everything else this is judged **at the moment of the operation**: the `vouched_key` and `member_id` in force at its HLC, and the key registered by then. The cloud's rule 12 does not ask whether a device belongs to nobody in the sense of this rule, but whether its `member_id` is empty. The app writes `vouched_key` whenever it says whose a device is, with the key it has registered for that device, and refuses to assign a device whose key it does not have yet; and an administrator's device vouches, once and in one operation (`library.vouch`), for every registered device that has a person and no `vouched_key`, with the key it has of it, at the end of a sync session.

14. **Echar a una persona (D98).** `member.access_withdrawn` (boolean; null or absent reads as false) says the person may no longer reach the library, from any device or through their account. The person stays in the catalog, with their name, copies and marks. **It is written by whoever may write `role`** (rule 3: an administrator); from anyone else, to withdraw or to give back, the operation is a request (the one exception is a person withdrawing **themself**, rule 15; **giving the access back is never theirs**, the person themself included), and so is a `create` of a member that carries the field. The cloud may not write it (rule 12). **A device of a person whose access is withdrawn belongs to nobody**, exactly like a device whose `vouched_key` does not match (rule 13): it counts as a reader, keeps no marks, and so on, in everything the judge asks about the person or the role of a device, judged at the moment of the operation (the value in force at its HLC). **The cloud does not link a device to such a person** (rule 12): that change is a request. The mark is not what stops a device by itself: the app writes it in one operation (`member.withdraw`) together with, for each device of the person, the take-away of its person and its vouched key, its fence (`trusted_through`, see the definition above), and its revocation (D71), so the devices also stop receiving the library; the mark is what makes no later route give the role back. Giving the access back removes the mark only: the devices stay without their person and revoked until an administrator links one again. A person with the access withdrawn keeps their role; the app does not let the last administrator who still has access be withdrawn.

15. **Leaving the library oneself (D102).** A person who is not an administrator (an administrator may do all of it anyway) may withdraw **their own** access, and cut off their own devices with it. The operation is signed by a device of that person, by rule 2: its `vouched_key` matches (rule 13) and their access is not withdrawn already. It is **allowed only if everything it carries is one of these**, and a single other change, or a missing condition, makes the **whole** operation a request (rule 5):
    - exactly one `member` `update` of **their own** person, whose fields are exactly `access_withdrawn: true` (rule 14);
    - for each device that **belongs to them in the state of whoever receives it** (the `member_id` of its `device` row points at them, whatever its `vouched_key` says): a `device` `update` whose fields are exactly `member_id: null` and `vouched_key: null`, the same one that expelling writes (rule 14). **For the signing device only**, also `trusted_through` equal to the `previous` of the operation (the empty text if it is `null`): its own fence, which disbelieves nothing it did, since all of it is an ancestor of its previous operation;
    - for such a device, a `revocation` `create` whose fields are exactly `device_id` (that device) and `device_name` (a text).

    Nothing else: no catalog change, no other person, no role, no other field, no device that is not theirs (nor one the receiver does not know yet: it is a request until that registration arrives, and then it is judged again, as always, rule 6), and the mark is never taken off (`false`) by them: giving the access back stays an administrator's (rule 14, SEG-032). A device with no person, or whose vouched key does not match, cannot leave for anyone.

    **Why their other devices are not fenced.** Expelling fences every device of the person, because the administrator who expels does not trust anything they say after. When a person leaves by themself, the fence would disbelieve the work of their other devices that the signing one has not seen yet, and other people may already have built on it (a book that a tablet created and somebody else edited); the fence would make that work a request and the edits that rest on it would be lost. That can happen to anybody who leaves with a phone that has not synced with their tablet, with no ill intent, so the rule does not allow it. What is left open is what they could already do before leaving: a device of theirs signing, later, an operation dated before their leaving. Leaving is voluntary, so whoever wants to keep writing has no need to leave and come back with false dates; and nobody closes it afterwards today: expelling the person again finds no device that points at them, `complete_withdrawals` does not see devices that already have no person, and withdrawing a device (D71) fences it only when it writes the revocation, which already exists here. Closing it would take a new action of whoever administers (fencing a device that is already withdrawn); it is not built.

    The app writes it in one operation (`member.leave`) with the same code as expelling (`cut_off_changes`). It does **not** remove the library from the leaving device at once: the operation exists only there until it reaches another device; whoever receives it sends the proof (the signed revocation of that device) and the device removes the library, over the local network or through the cloud, like any revoked device. The cloud cuts their account as soon as it applies the mark.

`conformance/permissions.json` has cases in the shape of the merge cases (`operations`, `deliveries`), with `expect` listing the ids of the operations that end **applied**, those that end as **requests**, and, optionally, those **rejected** (not stored at all, like an unsigned one); every delivery order must give the same lists. Deliveries keep each device's own operations in order (each one follows its `previous`), as the sync protocol does, so a device's key registration always comes before its signed operations. Every operation is signed with the test key of `conformance/signatures.json`, except those marked `"unsigned": true` (a field of the case, not of the operation), which every implementation must refuse.

The merge cases (`conformance/library-merge.json`) are written without signatures and without key registrations, to keep them about merging: each implementation registers every author of a case with the test key before delivering it (a `device` row it then leaves out of the comparison) and signs every operation with that key.

## Running the conformance cases

Each implementation loads the files in `conformance/` (not `conformance/draft/`) in its test suite and checks that every case produces the expected result. The Rust implementation does this in `crates/domain/src/operation.rs` (validation), `crates/domain/src/signature.rs` (signatures) and `app/src-tauri/src/sync.rs` (merging and permissions, all four files). The PHP server runs the validation and signature cases (`server/tests/Validator/`, `server/tests/Sync/`) and, since milestone 7.4.4, the merge cases of `library-merge.json` and `merge.json` against its merge engine (`server/tests/Sync/Merge/`); the case about two operations with one HLC it will cover when the engine is plugged into the push (7.4.6). Since milestone 7.4.5 it also runs `permissions.json` against its judge (`server/tests/Sync/Permission/`), in every delivery order and again after judging the whole log from scratch; the operations a case expects `rejected` do not reach the judge, and will be checked with the whole `push` in milestone 7.4.6.

## Merging operations from several libraries

`conformance/library-merge.json` describes how a device applies operations received from other devices when they belong to different libraries. Each case has:

- `operations`: full operations, with their library and HLC.
- `deliveries`: orders in which to deliver them, as lists of indexes into `operations`. Each operation is delivered alone, in that order, as if it came in its own sync. **Every order must end in the same state.** Orders respect causality, as the sync protocol guarantees: a change to a row never arrives before the operation that created that row (a device always sends everything the other lacks, oldest first).
- `expect.rows`: every catalog row that must exist afterwards, as `{ library, entity, id, fields }`. Rows not listed must not exist. Fields not listed must be null: an optional field nobody set, such as a member's `role`, is left out.
- `expect.rejected` (optional): the ids of the operations that are **refused**, that is, not stored (see `previous` and the HLC rule below). When present, every other operation of the case must be taken, in every delivery. A skipped *change* (see below) is not a refused operation. When absent, the case does not say.
- A delivery may **repeat an index**: the same operation delivered again, as a device that asks twice. The second time changes nothing and is not refused.

Rules these cases pin down:

- A row is identified by **library, entity and id** together. Field versions and tombstones are kept per library too, so nothing done in one library affects another.
- Changes apply **even if the library row has not arrived yet**: the library is only the scope, not a parent row that must exist first.
- **Deleting the library** leaves a tombstone for the whole library: its rows are removed, and any later change in that library is ignored, whatever its HLC. The delete wins, as it does for any row.

## Merging operations within a library

`conformance/merge.json` is the same kind of case with one library. Every operation in it has the `previous` of its author's chain and every delivery keeps each author's operations in order, except in the one case about two operations with the same HLC. Where an operation needs a row, that row's creation comes first in every delivery (causality, as above). The rules:

- **Field by field.** A change to a row only touches the fields it names. Each field of each row remembers the HLC of the change that wrote it; a change writes a field only if its HLC is **greater** than the remembered one. Two devices that change different fields of one row keep both changes.
- **Last writer per field.** The HLC text order decides: milliseconds, then counter, then the device id as text (a higher counter beats a higher device id in the same millisecond). The result is the same in any delivery order. A tie is not newer: the same HLC never overwrites a field.
- **A change keeps the versions of the fields it lost.** A change that loses one field and wins another writes only the one it won and leaves the lost field's remembered HLC where it was, so a third change dated between the two cannot win the field later.
- **Delete wins, with tombstones.** A delete removes the row and leaves a tombstone with the row's entity and id. Whatever arrives afterwards for that row is ignored, whatever its HLC: an update, or a create with the same id. A delete also beats an update that has a higher HLC, in either order of arrival. Rows that hang from the deleted one (its `work_tag`, `series_entry` and the like) go with it, but they get no tombstone of their own.
- **A delete wins over what depends on it (D89).** A **required** reference (a field that every row of its entity must have: `edition.work_id`, `copy.edition_id`, `work_contributor.person_id`) means the row goes with the row it points to, all the way down (a deleted work takes its editions and their copies). An **optional** reference (`edition.publisher_id`, `copy.owner_id`, `device.member_id`) means the row stays and just loses that reference. A create or update that arrives after the delete and names the deleted row in an optional reference is **applied with that field set to null** (its field version written as usual, the rest of the change untouched); with a required reference it is skipped, as a broken reference is. So every delivery order ends with the same rows.
- **Delivering an operation twice changes nothing.** An operation already stored is counted as known and skipped.
- **A broken reference skips the change, not the operation.** Each change is applied on its own: an update of a row that does not exist (never created, or removed with its parent), and a create or update whose reference points to a row that does not exist (a `copy` of an edition nobody has, a `work_tag` of a work already deleted), write nothing: no row, no field version, no tombstone. This holds for every reference in the schema, also for one a database would not enforce on its own (`device.member_id`: the app has no foreign key there, so it checks that the row exists, CON-007). The operation itself is stored and forwarded like any other, and its other changes apply.
- **Not from the future (SEG-028).** A receiver refuses (does not store) an operation whose HLC milliseconds are more than **one hour** (`MAX_CLOCK_DRIFT_MILLIS`, 3 600 000 ms, `crates/domain/src/hlc.rs`) ahead of its own clock, and holds back the next ones of its author like any refusal (their `previous` is missing). The app has always done this when it merges; the server does it on `push` (rejection `too_far_ahead`). An honest device never signs it: its clock is kept within the drift. Without it a single operation dated at the end of time lifts the floor of every HLC the library writes afterwards.
- **One HLC per operation.** HLCs are unique in a library's log: a second operation with an HLC already stored is **refused** (not stored), and so are the operations of its author that chain to it, because their `previous` is missing. Which of the two is kept depends on which arrives first; the case delivers the first one first. This is a rule about a modified app: an honest device never signs two operations with one clock reading.
